Executive answer

Use the open Agent Skills specification as the compatibility boundary. Maintain one canonical package per skill and adapt only its installation location. This is broader and safer than declaring separate “Codex,” “Claude,” or “Gemini” variants, which drift as providers evolve.

Compatibility means: a supported host can discover, parse, select, and load the same package without a schema fork. Runtime tools and credentials remain explicit prerequisites.

The portable contract

Schema

Only standard root fields

name, description, license, compatibility, and a string-to-string metadata map. Broville arrays and objects are preserved as JSON strings inside metadata.

Behavior

Capabilities, not tool identifiers

Skills ask the host for navigation, browser inspection, scheduling, or connected-service capabilities. They do not assume another provider’s function names or argument shapes.

Packaging

Complete ordinary copies

The installer copies SKILL.md and all relative resources. Symlinks, bytecode, machine-specific paths, secrets, and divergent provider copies are rejected.

Selection

Descriptions carry routing context

Agents discover only concise metadata first, then load the full instructions and supporting resources when the user’s task matches.

Repository changes

  1. Migrated every skill from Broville-only root fields to the open schema and applied a major version bump for the metadata-contract change.
  2. Preserved author, version, platforms, triggers, inputs, outputs, tags, aliases, provenance, and relationships in string-valued metadata.
  3. Removed dangling references to packages that do not exist and replaced only those with relevant in-repository relationships.
  4. Made browser, Cloudflare integration, cross-model review, context-file, and scheduler instructions host-neutral.
  5. Removed a tracked CPython bytecode artifact and prohibited non-portable generated package files.
  6. Added a cross-platform installer, official-plus-policy validator, smoke tests, CI matrix, specification, and operating-procedure updates.

Boundaries and future-proofing

  • No finite list can guarantee compatibility with every present or future product. The defensible guarantee is conformance to the open standard plus tested adapters for documented hosts.
  • A schema-valid skill can still require a browser, CLI, network access, credentials, operating system, or connected integration that a particular session lacks. Skills must state and check those prerequisites.
  • Provider extensions such as custom icons, invocation controls, or tool allowlists are intentionally excluded from canonical entrypoints because another host may reject or ignore them.
  • New hosts should receive a discovery adapter only after their primary documentation confirms a path. The package schema should not change for an installation path.
